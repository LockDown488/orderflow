# OrderFlow — бизнес-правила MVP
Версия: 1.0 (проектное предложение, 15.11.2026)

## Роли
- `CUSTOMER`: собственный профиль, каталог, своя корзина, создание и просмотр собственных заказов, запуск mock-оплаты своего заказа.
- `MANAGER`: управление категориями и товарами, изменение складских остатков, просмотр всех заказов. Не управляет пользователями и ролями.
- `ADMIN`: все действия менеджера, просмотр пользователей и назначение ролей. Изменение своей роли/отключение последнего администратора запрещено.

## Каталог и корзина
- Цена строго положительная, валюта MVP — RUB, две десятичные позиции; товар может быть активным/неактивным.
- Неактивный товар нельзя добавить в корзину или оформить, но он остаётся в истории заказов.
- В корзине не более одной строки на товар; количество — положительное целое.
- Цена в корзине информационная: окончательная цена фиксируется при создании заказа.

## Остатки и резерв
- Один склад на весь магазин; отрицательные остатки запрещены.
- При оформлении проверяются активность товара и наличие количества; резерв выполняется атомарно для всех позиций.
- Конкурирующие заказы не должны резервировать один и тот же последний экземпляр. Использовать блокировку строки `inventory` (например, `SELECT ... FOR UPDATE`) в фиксированном порядке `product_id` и транзакцию БД; подтвердить интеграционным тестом.
- При резерве `available -= quantity`, `reserved += quantity`; при успешной оплате `reserved -= quantity`; при отмене/неуспешной оплате `reserved -= quantity`, `available += quantity`.
- Складские изменения менеджера не могут сделать `available_quantity` отрицательным. Удаление товара с активным резервом запрещено (в MVP — soft deactivate).

## Заказы и оплата
- Заказ создаётся только из непустой корзины; все товары должны быть активны и доступны.
- Сумма = сумма `unit_price * quantity` по снимкам строк заказа, вычисляется сервером; клиент не передаёт итоговую сумму как источник истины.
- Создание заказа и резервирование — одна транзакция; при ошибке всё откатывается. Корзина очищается только после успешного создания заказа.
- Статусы заказа: `PENDING_PAYMENT`, `PAID`, `CANCELLED`.
- Статусы оплаты: `PENDING`, `SUCCEEDED`, `FAILED`.
- Mock-оплата выполняется по явному запросу покупателя: в тестовом запросе `outcome=SUCCESS|FAILURE`. Это симулятор, не подключение к платёжному провайдеру.
- Успех: `PENDING_PAYMENT -> PAID`, `PENDING -> SUCCEEDED`, резерв списывается; ошибка: `PENDING_PAYMENT -> CANCELLED`, `PENDING -> FAILED`, резерв возвращается.
- Покупатель может отменить только `PENDING_PAYMENT`, после чего резерв возвращается. `PAID` нельзя отменить в MVP (возвраты — будущий этап).
- Повторная обработка того же завершённого платежа не должна повторно менять остатки; при конфликтующем повторном запросе возвращается 409. Параллельные запросы защищены блокировкой/условным обновлением.
- Автоматическое истечение резерва, доставка, возвраты и повторные попытки платежа не входят в MVP. Поэтому неоплаченный заказ сохраняет резерв до явной оплаты/отмены; это сознательное ограничение первой версии.

## API и ошибки
- Авторизация JWT; пароли хранятся только как стойкие хэши (например, BCrypt).
- Валидация входных DTO; 400 для неверных данных, 401 для отсутствующей/неверной аутентификации, 403 для недостаточных прав, 404 для отсутствующего или чужого ресурса, 409 для бизнес-конфликтов.
- Единый JSON-формат ошибок (Problem Details / RFC 9457), без утечек внутренних деталей.
- Транзакции и бизнес-инварианты проверяются интеграционными тестами с PostgreSQL.
