# OrderFlow — техническое задание MVP
Версия 1.0 · 15.11.2026 · Статус: проект для согласования

## 1. Назначение
Backend-платформа одного интернет-магазина: каталог, корзина, заказ, резерв единого склада и имитация оплаты. Учебный проект с production-like инженерными практиками. Frontend не входит в MVP.

## 2. Зафиксированные решения
Один магазин (`single`), роли `CUSTOMER`/`MANAGER`/`ADMIN` (`three`), один склад (`single`), встроенный mock payment (`mock`), минимальный MVP (`mvp`), modular monolith.

## 3. Технологии
Java 21; Spring Boot 3.x (актуальную поддерживаемую версию уточнить перед инициализацией); Spring MVC; Spring Data JPA; Spring Security/JWT; Jakarta Validation; PostgreSQL; Liquibase; Gradle; Docker Compose; OpenAPI; JUnit 5, Mockito, Testcontainers. `BigDecimal` для денег, `UUID` для ID. Никаких внешних платёжных интеграций.

## 4. Функциональные требования
- FR-01 Регистрация покупателя по email/паролю и JWT-аутентификация.
- FR-02 Разграничение ролей: CUSTOMER, MANAGER, ADMIN.
- FR-03 Публичный просмотр активных товаров, пагинация, фильтр по категории.
- FR-04 Управление категориями/товарами менеджером; деактивация вместо удаления.
- FR-05 Управление доступным остатком товара менеджером.
- FR-06 Корзина покупателя: просмотр, добавление, изменение количества, удаление позиции.
- FR-07 Создание заказа из корзины с серверным расчётом цены, snapshot позиций и атомарным резервом.
- FR-08 Просмотр покупателем своих заказов и деталей; менеджером — всех заказов.
- FR-09 Mock-оплата: детерминированный SUCCESS/FAILURE, атомарное обновление заказа, платежа и резерва.
- FR-10 Отмена неоплаченного заказа с освобождением резерва.
- FR-11 Администратор может просматривать пользователей и менять роли с защитой от удаления последнего ADMIN.

## 5. Основные REST endpoints (черновой контракт)
| Method | Path | Роль | Назначение |
|---|---|---|---|
| POST | /api/v1/auth/register | public | Регистрация CUSTOMER |
| POST | /api/v1/auth/login | public | Выдача JWT |
| GET | /api/v1/products | public | Активный каталог |
| GET | /api/v1/products/{id} | public | Карточка товара |
| POST | /api/v1/categories | MANAGER/ADMIN | Категория |
| POST | /api/v1/products | MANAGER/ADMIN | Товар |
| PATCH | /api/v1/products/{id} | MANAGER/ADMIN | Изменение/деактивация |
| PUT | /api/v1/inventory/{productId} | MANAGER/ADMIN | Установка доступного остатка |
| GET | /api/v1/cart | CUSTOMER | Своя корзина |
| PUT | /api/v1/cart/items/{productId} | CUSTOMER | Установить количество |
| DELETE | /api/v1/cart/items/{productId} | CUSTOMER | Удалить позицию |
| POST | /api/v1/orders | CUSTOMER | Создать заказ |
| GET | /api/v1/orders | CUSTOMER | Свои заказы |
| GET | /api/v1/orders/{id} | CUSTOMER | Свой заказ |
| POST | /api/v1/orders/{id}/cancel | CUSTOMER | Отменить неоплаченный |
| POST | /api/v1/orders/{id}/payment | CUSTOMER | Mock-оплата |
| GET | /api/v1/management/orders | MANAGER/ADMIN | Все заказы |
| GET | /api/v1/admin/users | ADMIN | Пользователи |
| PATCH | /api/v1/admin/users/{id}/role | ADMIN | Изменение роли |

`PUT /cart/items/{productId}` принимает `{ "quantity": 2 }`. `POST /orders/{id}/payment` принимает `{ "outcome": "SUCCESS" }` или `FAILURE` только в учебном окружении; это явно тестовый контракт, не безопасный реальный payment API.

## 6. Модель данных
См. `data-model.md`: users, categories, products, inventory, carts, cart_items, orders, order_items, payments. Бизнес-ограничения и переходы состояний — `business-rules.md`.

## 7. Нефункциональные требования
- NFR-01 Все миграции схемы через Liquibase; `ddl-auto=validate`.
- NFR-02 Единый формат ошибок, входная валидация, отсутствие секретов в репозитории.
- NFR-03 Логирование важных бизнес-событий без паролей/JWT/PII в открытом виде.
- NFR-04 Unit-тесты правил; integration-тесты с Testcontainers/PostgreSQL на создание заказа, конкурентный резерв, оплату и отмену.
- NFR-05 Сборка и тесты запускаются одной Gradle-командой; приложение и PostgreSQL — через Docker Compose.
- NFR-06 Swagger/OpenAPI, README с инструкциями запуска, архитектурное описание и ADR.
- NFR-07 Транзакционная целостность: невозможны отрицательные остатки, двойное списание резерва и частично созданные заказы.
- NFR-08 API versioning `/api/v1`; пагинация списков; предсказуемые HTTP-коды.

## 8. Модульная структура
`identity`, `catalog`, `inventory`, `cart`, `order`, `payment`, `shared`. Общая БД, но логика разделена по модулям; зависимости направленные, межмодульные обращения через сервисные интерфейсы, без прямого доступа к чужим репозиториям.

## 9. Критерии приёмки
1. Покупатель регистрируется, входит, получает JWT; CUSTOMER не может менять товары и роли.
2. Менеджер создаёт активный товар, устанавливает остаток 1.
3. Покупатель оформляет заказ на 1 шт.; available становится 0, reserved становится 1.
4. Второй конкурентный заказ на тот же последний экземпляр не создаётся, отрицательных остатков нет.
5. SUCCESS переводит заказ в PAID, reserved в 0; повторный вызов не списывает второй раз.
6. FAILURE переводит заказ в CANCELLED и возвращает 1 в available.
7. Отмена PENDING_PAYMENT возвращает резерв; отмена PAID возвращает 409.
8. Цена в существующем заказе не меняется при изменении цены товара.
9. Пользователь не видит чужие заказы.
10. Все миграции, unit/integration-тесты и локальный запуск описаны и воспроизводимы.

## 10. Вне рамок MVP
Доставка, уведомления, email-подтверждение, refresh tokens, промокоды, несколько валют и складов, реальные платежи, возвраты, повторные попытки платежа, таймаут резерва, RabbitMQ, Redis, Kubernetes, frontend, распределённые транзакции.

## 11. Предлагаемый порядок реализации
1. Репозиторий, Gradle, Compose, Liquibase, CI skeleton.
2. Identity + Security + Catalog.
3. Inventory + Cart.
4. Order + атомарный резерв + concurrency tests.
5. Payment mock + cancel + идемпотентность.
6. OpenAPI, документация, интеграционные тесты и проверка критериев приёмки.

## 12. Открытые решения
- Политика изменения остатка менеджером: в MVP изменяется только `available_quantity`, а не физический общий остаток.
- Для MVP одна попытка оплаты на заказ; дальнейшие retry потребуют расширения модели.
- Таймаут неоплаченного резерва отсутствует; добавить отдельным этапом.
- Валюта зафиксирована как RUB в учебном MVP, без мультивалютности.
